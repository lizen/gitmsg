# 결정 기록

2026-09-14 브레인스토밍 세션에서 오간 질문과 선택, 그 근거를 남긴다.
왜 이렇게 만들었는지 나중에 되짚을 때 쓰려는 문서다.

## 출발점

> 현재 노트북의 Nativ 앱에 로드한 LLM 모델을 활용하려고 한다.
> Nativ 앱의 REST API를 사용하여 특정 폴더의 IntelliJ IDEA 프로젝트의 branch에서
> commit할 대상 파일을 검토하여 commit 메시지를 자동으로 생성하기 위한 계획을 작성해보자.

## 먼저 확인한 것

설계를 시작하기 전에 환경을 직접 조사했다. 추측으로 정하면 나중에 전부 뒤집힌다.

### 대상 저장소

IntelliJ 최근 프로젝트 목록에 `~/work/` 아래 저장소가 20개 넘게 있었다.
**한 곳이 아니라 여러 곳을 오가는 구조**라는 게 설계에 결정적이었다.

`example-backend` 최근 non-merge 커밋 5건의 diff 크기: 16 / 53 / 120 / 165 / 882줄.

커밋 제목 스타일이 저장소마다 갈렸다.

| 스타일 | 실제 예 |
|---|---|
| 키 접두 | `ABC-1858 Teradata 갭분석 마이그레이션 정비` |
| 대괄호 접두 | `[XYZ-248] fix: 결재 역할 팝업창 중복 제거` |
| 괄호 접미 | `fix(quality): ... (DEF-119)` |
| Conventional Commits | `ci: auto build/publish on tag push` |
| 키 없는 한국어 | `pg db업그레이드에 따른 쿼리문 변경` |

브랜치명도 `ABC7-24`, `hotfix/JKL-4146`, `feature/DEF-119`처럼 키가 있는 것과
`dev`, `master`, `main`, `develop`, `release-adv`, `fetchUserProfile`처럼
없는 것이 섞여 있었다.

## 질문과 선택

### 1. 통합 지점 — 생성한 메시지를 어디서 받을 것인가

**선택: CLI 스크립트**

| 후보 | 판단 |
|---|---|
| **CLI 스크립트** | 채택. 저장소 20여 곳에 아무것도 심지 않아도 된다 |
| git `prepare-commit-msg` 훅 | 저장소마다 설치가 필요하고, 커밋할 때마다 LLM 대기가 걸린다 |
| IntelliJ External Tool | 커밋 메시지 입력란에 직접 쓸 수 없어 실익이 없다 |
| IDEA 플러그인 | 범위가 과도하게 커진다 |
| CLI + 훅 둘 다 | 지금은 CLI만으로 충분하다. 훅은 필요해지면 CLI를 부르는 래퍼로 얹으면 된다 |

### 2. 메시지 규칙 — 저장소마다 다른 형식을 어떻게 맞출 것인가

**선택: 저장소 히스토리 few-shot 자동 학습 + 브랜치 이슈 키 강제**

고정 규칙 하나로 통일하는 안은 기존 히스토리와 정면으로 충돌한다.
설정 파일로 저장소별 지정하는 안은 20여 곳을 수동 등록해야 한다.

실행 시점에 그 저장소의 최근 커밋을 읽어 예시로 넣으면 설정 없이 스타일이 맞는다.
다만 이슈 키만은 LLM이 지어내면 안 되는 값이라 코드로 처리한다.

### 3. 대상 범위 — 어떤 변경분을 볼 것인가

**선택: staged 우선, 비어 있으면 worktree diff로 fallback**

`git add`로 올린 것만 보는 안은 `add` 전에 미리 돌려보는 흐름을 막는다.
브랜치 전체(base 대비)를 보는 안은 일상 커밋에는 범위가 너무 넓다.
squash나 MR 설명이 필요해지면 그때 별도 옵션으로 다룬다.

### 4. 구현 방식

**선택: 단일 호출 + diff 예산 관리**

실측 diff가 대부분 1,000줄 미만이라 한 프롬프트에 들어간다.

map-reduce(파일별 요약 후 통합)는 대형 리팩터링에 강하지만,
로컬 30B 4bit에서 호출이 N+1번이면 체감 속도가 크게 나빠진다.
실측상 그럴 일이 드물어서 넣지 않았다. 필요해지면 그때 추가한다.

기존 CLI(`aichat` 등)에 Nativ를 백엔드로 연결하는 안은
저장소별 few-shot 자동 학습과 이슈 키 강제 주입을 지원하지 않는다.
앞뒤로 스크립트를 붙이면 결국 같은 분량의 코드를 짜면서 의존성만 늘어난다.

## 설계하며 뒤집힌 것

### 제목 길이 규칙을 넣지 않기로 했다

처음에는 "제목 50자 이내" 같은 통상적인 규칙을 시스템 프롬프트에 넣으려 했다.
그런데 실제 히스토리를 보니 `[DQ] DEF-166 샘플링 동일 업무영역 내 여러개의 계정에
샘플링 적용 안되는 오류 수정`처럼 50자를 훌쩍 넘는 제목이 흔했다.

길이 지시를 넣으면 few-shot 예시와 충돌한다. 길이는 예시가 가르치게 두고,
코드는 "제목은 한 줄"만 지킨다.

### 언어 플래그를 두지 않기로 했다

`--lang ko` 같은 옵션을 생각했지만, 시스템 프롬프트에
"저장소 히스토리와 같은 언어로 쓴다"를 넣는 것으로 대체했다.
예시가 한국어면 한국어가 나온다. 옵션이 하나 줄었다.

### 이슈 키 "강제"의 범위를 좁혔다

브랜치명에 키가 없는 경우가 생각보다 많았다. `dev`, `master`, `release-adv`,
`fetchUserProfile` 등. org-b 저장소는 커밋 제목 대부분이 키 없는 한국어였다.

그래서 강제는 **키가 있을 때만** 적용한다. 없는데 만들어내는 게 제일 나쁘다.

### 키 위치까지 히스토리에서 감지하기로 했다

키를 넣는 위치가 저장소마다 달랐다. 접두 / 대괄호 접두 / 괄호 접미.
어차피 "키가 빠졌을 때 코드가 붙이는" 후처리가 필요한데,
붙일 자리를 하드코딩하면 저장소 절반에서 어색해진다.

최근 커밋 제목 중 키를 포함한 것들을 세어 최빈 스타일을 고르기로 했다.
열 줄 남짓이고, 후처리 품질에 직접 기여한다.

## 미룬 것

| 항목 | 미룬 이유 |
|---|---|
| map-reduce 대형 diff 처리 (`--deep`) | 실측 diff가 작다. 지금 넣으면 안 쓰는 코드가 된다 |
| git 훅 연동 | CLI로 충분하다. 필요해지면 CLI를 부르는 래퍼면 된다 |
| IntelliJ 플러그인 | 범위가 과도하다 |
| 브랜치 전체(base 대비) 범위 옵션 | squash·MR 설명이 실제로 필요해질 때 |
| 설정 파일 | 자동 학습으로 대체된다 |
| 자동 커밋 | 확인 없이 커밋되는 경로를 만들지 않는다 |

## 남은 전제

구현이 끝나도 사용 전에 사람이 해야 하는 일이 있다.

1. **Nativ 앱에서 로컬 API 서버를 켠다.** 조사 시점에 꺼져 있었다
2. 모델을 로드한다
3. `~/.local/bin`이 PATH에 있는지 확인한다

응답 시간은 아직 측정하지 않았다. 구현 계획 Task 9에서 처음 잰다.
